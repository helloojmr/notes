## 接口自动化测试框架

### 框架思想

- **用例管理**：测试代码层面的组织方式
  - **API 封装**：将接口请求抽象为类或方法(如 `api` 目录)，供用例调用
  - **数据库封装**：封装数据库操作(连接、查询、断言数据)，用于数据准备或结果验证
  - **测试数据参数化**：将测试数据与代码分离，实现数据驱动，提高维护性
  - **代码优化**：断言封装(通用断言函数)、日志、配置管理等，让用例更简洁
- **被测系统**：测试的目标环境
  - **应用服务器**：提供 HTTP 接口的服务端
  - **数据库**：存储业务数据，测试时可能需要验证数据一致性或清理脏数据
- **交互方式**：通过 HTTP 请求测试应用服务器，通过数据库工具类直接操作数据库。

### 设计思路

1. **搭建基础框架**
  - 定义项目目录结构：按功能划分文件夹(如 `api`、`scripts`、`data` 等)
  - 安装依赖包：`requests`、`pymysql`、`unittest`/`pytest`、`ddt`、`HTMLTestRunner` 等
2. **通用功能类封装**
  - 数据库工具类：封装数据库连接、增删改查、断言数据是否存在等通用方法，供数据准备或清理
  - 其他通用类：日志工具、配置读取、发送邮件等
3. **用例基础代码**
  - 封装接口 API 对象：`api` 目录下为每个业务模块创建接口类，封装请求方法
  - unittest 编写测试脚本：`scripts` 目录下继承 `unittest.TestCase`，调用接口对象，添加断言
4. **测试数据参数化**
  - 测试数据 JSON 文件设计：`data` 目录存放测试数据，每个文件对应一个接口或模块的数据集，含多组输入和预期结果
  - 参数化实现：读取 JSON 文件，通过 `@ddt` 或 `@pytest.mark.parametrize` 逐条注入测试方法，"一次编写，多数据运行"
5. **用例组织运行**
  - 组织测试用例：通过测试套件(如 `unittest.TestSuite`)或按目录自动发现用例
  - 生成测试报告：运行后生成 HTML 报告到 `report` 目录
  - 提供执行入口：`run_suite.py` 总控脚本，可配置测试范围、环境、报告输出

### 项目目录结构详解

#### 目录结构

```
apiTestFramework #项目名称
|-api #接口对象层：每个模块一个类，封装接口请求（技术实现细节，不涉及业务断言。）
|-scripts #测试用例层：存放 unittest 测试脚本，调用 api 层（业务逻辑验证，依赖 api 层和数据文件。）
|-data #测试数据：JSON/YAML 文件，与测试用例分离（纯数据，与代码完全分离。）
|-report # 测试报告：运行后自动生成的 HTML 报告
|-common # 通用工具类：数据库连接、日志、配置读取、断言封装等（基础工具，供其他层调用。）
|-config.py # 全局配置：如环境地址、数据库连接信息、超时时间等（集中管理配置，避免硬编码。）
|-run_suite.py # 测试执行入口：加载用例、运行、生成报告
```

#### 框架工作流程

1. **配置加载**：`run_suite.py` 读取 `config.py`，获取测试环境地址、数据库连接等信息。
2. **数据准备**：测试用例从 `data` 目录读取 JSON 数据文件，准备测试数据。
3. **接口调用**：测试用例实例化 `api` 层中的接口对象，传入数据，发起请求。
4. **断言验证**：对响应结果进行断言，可能还会通过 `common` 层的数据库工具查询数据库进行数据一致性验证。
5. **报告生成**：所有用例执行完后，`run_suite.py` 生成 HTML 报告到 `report` 目录。
6. **结果通知**：可扩展发送邮件或集成 CI 系统。
