## 性能瓶颈分析与调优

- 压测结果不达标时，按**客户端 → 网络 → 应用 → 中间件 → 数据库**的链路逐层排查。
- **通用定位思路（配合 Linux 笔记中的命令）**：
  1. **先看整体资源**：`top`（CPU/负载）、`free -h`（内存）、`df -h`（磁盘）、`vmstat 1`（运行队列 r / IO 等待 b / swap si-so）。
  2. **CPU 高**：
     - 用户态高（us 高）：业务计算密集，Java 应用用 `jstack` 抓线程堆栈，定位死循环/热点代码。
     - 系统态高（sy 高）：频繁系统调用（如日志刷盘、锁竞争）。
     - 等待 IO（wa 高）：磁盘或网络瓶颈，用 `iostat -x` 看 `%util`、`await`。
  3. **内存问题**：内存持续增长 → 内存泄漏（反复压测观察趋势）；频繁 GC 停顿 → JVM 参数调优。
  4. **数据库**：开启慢查询日志定位慢 SQL；检查连接池是否耗尽（连接数满）、锁等待。
  5. **中间件 / 线程池**：线程池队列堆积、超时配置过短、连接池参数不合理。
  6. **网络**：带宽打满、`TIME_WAIT` 连接过多（`netstat -anp | grep TIME_WAIT`）。

- **CPU 100%，TPS 不涨**
  - 可能瓶颈：死循环、热点代码、GC 频繁
  - 排查命令：`top` → `jstack`、`jstat -gc`
- **内存持续增长**
  - 可能瓶颈：内存泄漏
  - 排查命令：`top`（RES 趋势）、MAT/LeakCanary
- **磁盘 IO 高**
  - 可能瓶颈：日志刷盘、索引碎片、无缓存查询
  - 排查命令：`iostat -x`（%util/await）、`vmstat`（b/wa）
- **数据库连接满**
  - 可能瓶颈：连接池太小、慢 SQL 占用
  - 排查命令：`show processlist`、慢查询日志
- **端口 TIME_WAIT 多**

- **面试话术**：压测时发现 CPU 飙高，先用 `top` 定位进程，再用 `jstack` 抓线程堆栈定位到具体代码行，发现是日志刷盘太频繁，优化后 TPS 提升 30%。

## 场景模型与测试数据准备

- **业务模型**：确定被测业务及占比，如 80% 用户是浏览、20% 是下单，压测按比例混合请求，模拟真实流量。
- **用户模型**：用户操作路径、思考时间（Think Time）、用户行为分布（新老用户、不同入口）。
- **数据模型**：
  - **数据量**：尽量贴近生产数据量（千万级用户、百万级订单）。数据量过小测不出真实性能（如索引失效、分页慢）。
  - **数据分布**：热点数据（爆款商品）、冷热数据比例。
  - **数据状态**：新数据 vs 历史数据，查询性能差异明显。
- **测试数据准备**：
  - 造数方式：接口造数 / 直连数据库批量插入（可参考 SQL 笔记）。
  - 数据隔离：压测数据与开发/功能测试数据隔离，避免相互干扰。
  - 数据清理：压测结束后清理脏数据，保证环境可重复使用。
