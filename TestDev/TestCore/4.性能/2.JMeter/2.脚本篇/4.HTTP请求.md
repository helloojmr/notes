## HTTP 请求取样器面板与核心字段

- **位置**：线程组 → 添加 → 取样器(Sampler) → HTTP 请求。
- **Web 服务器区**
  - **协议(Protocol)**：`http` 或 `https`。
  - **服务器名称或 IP(Server Name or IP)**：如 `example.com`、`192.168.1.10`。
  - **端口号(Port Number)**：如 `80`、`443`、`8080`；留空则按协议默认端口。
- **HTTP 请求区**
  - **方法(Method)**：GET / POST / PUT / DELETE / PATCH / HEAD 等，下拉选择。
  - **路径(Path)**：接口路径，如 `/api/login`。
  - **内容编码(Content encoding)**：如 `UTF-8`，解决中文乱码。
- **对应代码**：`requests.get(url, params=...)`、`requests.post(url, json=...)`，取样器就是把这两行代码可视化。

## URL 拆解与内容落位(新手必看)

- **核心**：URL 是一个整体，JMeter 把它拆成几个输入框，按"这段内容是什么角色"放对位置。
- **URL 五段拆解**：`http://`(协议) + `www.example.com`(服务器) + `:8080`(端口) + `/api/user/login`(路径) + `?name=tom&age=18`(查询参数)。
- **对应 JMeter 位置**
  - 协议 → 协议(Protocol) 下拉框，选 http / https
  - 服务器 → 服务器名称或 IP 输入框，填域名
  - 端口 → 端口号输入框（http 默认 80 可不填）
  - 路径 → 路径(Path) 输入框，**只填 `?` 之前的部分**
  - 查询参数 → 参数区(Parameters)，GET 时自动拼到 URL 问号后
- **最容易踩的坑**：路径框只写 `?` 之前，`?` 后面的查询参数拆开放到参数区，别整段 URL 一起填。

### GET 与 POST 数据去向

- **GET**：数据在 URL 上。
  - 参数区填的键值对 → 自动拼到 `?` 后，浏览器可见、有长度限制，适合少量简单参数。
  - 服务端从 URL 参数取：`request.args` / `@RequestParam`。
- **POST**：数据在 body 里。
  - 参数区 → 表单(urlencoded) 进 body
  - Body Data → JSON 原始报文进 body
  - 文件上传区 → 文件(multipart) 进 body
  - 服务端从 body 取：`request.form` / `request.json` / `request.files`。

### 判断口诀

- URL 里有 `?` → 问号前进路径框，问号后的键值对进参数区
- 请求体是 `{...}` JSON → Body Data + Content-Type 头
- 请求体是 `a=1&b=2` 表单 → 参数区(POST 自动进 body)
- 请求体是文件 → 文件上传区
- 没有请求体(纯查询) → 只有路径框 + 参数区

## 参数(Parameters)与消息体数据(Body Data)

### Parameters

- 键值对形式，Name / Value 两列，可加注释。
- **GET 请求**：参数自动拼到 URL 问号后面，如 `/api/search?keyword=jmeter`。
- **POST 表单**：以 `application/x-www-form-urlencoded` 提交（浏览器表单默认格式）。
- 勾选 **Use multipart/form-data for POST**：表单以 multipart 方式提交，文件上传场景必选。
- **测开**：两种编码格式的区别——urlencoded 是 `&` 连接的纯文本键值对，multipart 用 boundary 分隔且支持二进制文件；服务端解析入口不同(表单参数 vs 文件流)；选型标准就是有没有文件。

### Body Data

- 原始报文，直接粘贴请求体文本。
- **POST JSON**：`{"username":"test","password":"123456"}`，提交 JSON 必须配合请求头 `Content-Type: application/json`，否则服务端大概率返回 415。
- 也支持 XML、纯文本，直接按接口文档写。

## 常见请求类型配置

- **GET 请求(查询类)**
  - 例：`GET http://api.shop.com:8080/api/search?keyword=手机&page=1`
  - 路径 `/api/search`(`?` 后不填)；参数区 `keyword=手机`、`page=1`
- **POST 请求(表单类)**
  - 例：`POST http://api.shop.com:8080/api/order`，字段 `goodsId=1`、`num=2`
  - 参数区填表单字段(POST 时参数区进 body，不拼 URL)，模拟网页表单提交
- **POST 请求(JSON 类)**
  - 例：`POST http://api.shop.com:8080/api/login`，body `{"username":"tom","password":"123456"}`
  - Body Data 填整段 JSON；Header Manager 加 `Content-Type: application/json`；参数区留空
- **文件上传**
  - 例：`POST http://api.shop.com:8080/api/upload`，multipart 字段名 `file`
  - 文件上传(Files Upload)区：文件路径、参数名、MIME 类型；勾选 multipart
- **测开**：一个接口的三种传参方式(GET Query / 表单 / JSON)是接口测试基本功，JMeter 里全部落在 Parameters 与 Body Data 两个区域的切换上。

## 高级选项(Advanced)

- **超时设置**
  - **Connect Timeout(连接超时)**：建立 TCP 连接的最大等待时间。
  - **Response Timeout(响应超时)**：发出请求后等待响应的最大时间。
  - 压测意义：不设响应超时，服务端无响应时线程一直挂起，会造成并发堆积、压测数据失真。
- **重定向设置**
  - **Redirect Automatically**：自动重定向，不记录中间跳转(单条采样)。
  - **Follow Redirects**：跟随重定向，记录每一次跳转(多条采样)。
  - 压测登录场景勾选 Follow Redirects，模拟真实用户 302 → 首页的完整链路。
- **Use KeepAlive**：使用长连接，默认勾选，模拟浏览器行为，减少 TCP 握手开销。
- **Browser-compatible headers**：模拟浏览器请求头，一般不用。

## HTTP Header Manager(请求头管理器)

- **添加路径**：右键线程组(或 HTTP 请求) → 添加 → 配置元件 → HTTP 头管理器；它是独立元件，不在 HTTP 请求面板里。
- **填写方式**：面板是 Name / Value 两列表格——名称列填 `Content-Type`，值列填 `application/json`；加更多头就点 Add 加行。
- **作用**：为请求添加或覆盖请求头。
- **常见请求头**：`Content-Type`、`Authorization`(token)、`User-Agent`、`Accept`、`Referer`。
- **典型场景**：压测需要鉴权的接口，Header 里加 `Authorization: Bearer ${token}`，token 由登录接口后置处理器提取后引用。
- **作用域**：放线程组层 → 组内所有请求生效；放单个取样器下 → 只对该请求生效。
- **何时需要**：POST JSON 必加(否则 415)；GET 一般不加；带 token 时加 `Authorization` 行。
- **对应代码**：`requests.post(url, headers=headers)`。

## HTTP Cookie Manager(Cookie 管理器)

- **作用**：管理 Cookie，模拟浏览器会话。
- **工作机制**：自动保存服务端返回的 `Set-Cookie`，后续请求自动携带。
- **典型场景**：压测登录后的业务接口 → 先登录拿 Cookie，再压业务接口，会话自动保持。
- **多线程注意**：默认 Standard 模式，每个线程维护各自独立的 Cookie 池，互不干扰。
- **对应代码**：`requests.Session()`。

## HTTP Cache Manager(缓存管理器)

- **作用**：模拟浏览器缓存行为，静态资源(JS/CSS/图片)只加载一次。
- **使用场景**：模拟真实用户浏览器访问的端到端压测。
- **注意**：纯接口压测(直接打 API)通常不需要，加了反而让缓存命中掩盖真实接口压力。
- **测开**：压测目标决定加不加——测"用户体感"加缓存，测"服务端容量"不加。

## HTTP Request Defaults(请求默认值)

- **作用**：抽取公共配置(协议、服务器、端口、路径前缀)，避免每个请求重复填写。
- **配置方式**：放在线程组层 → 组内所有 HTTP 请求自动继承，子请求只需填相对路径和各自参数。
- **对应代码**：`BASE_URL = "http://example.com"` 统一封装，请求只写相对路径。
- **面试话术**：多个接口共用一个服务器地址，用 HTTP Request Defaults 收口，改环境只改一处。

## 内容编码与中文乱码

- **现象**：查看结果树里响应中文乱码。
- **原因**：服务端响应头未带 `charset` 时，JMeter 默认按 `ISO-8859-1` 解码。
- **解决**：请求中内容编码填 `UTF-8`；或改 `jmeter.properties` 中默认编码配置。

## 测开视角:压测实战要点

- **token 链路**：登录接口 → 后置处理器提取 token → `${token}` 引用到 Header Manager，是接口压测标准套路。
- **响应超时**：务必设置 Response Timeout，防止线程挂死造成"假并发"。
- **面试话术**：HTTP 请求取样器 = 协议 + 服务器 + 端口 + 路径 + 方法 + 参数，本质就是 `requests` 库一行代码的可视化；性能测试的请求配置与接口自动化完全同源。
- **常见报错排查**：415 / 302 / 乱码等见「实战案例 → 实战排查」。

## 实战案例

### 案例一：登录接口压测(POST JSON + CSV 参数化)

- 场景：压测登录接口 `/api/login`，100 并发，每线程取不同账号，避免同一账号重复登录被服务端限流/踢下线。
- 准备 `users.csv`（放 JMeter bin 目录）：两列 `username,password`，几百行账号。
- 配置步骤：
  - 线程组：线程数 100、Ramp-Up 10、循环次数 10
  - 添加 CSV Data Set Config：文件名 `users.csv`、变量名 `username,password`、线程共享模式选当前线程
  - HTTP 请求：方法 POST、路径 `/api/login`、Body Data `{"username":"${username}","password":"${password}"}`
  - HTTP Header Manager：`Content-Type: application/json`
  - 响应断言：响应文本包含 `"code":0`
  - 监听器：查看结果树(调试用) + 聚合报告(看指标)
- 命令行正式跑：`jmeter -n -t login.jmx -l result.jtl -e -o report`。
- **测开**：参数化是压测数据的核心，CSV 变量 `${username}` 就是 Python 里遍历 `user_list` 取账号的 JMeter 版。

### 案例二：登录拿 token → 压测业务接口(关联)

- 场景：查询订单接口 `/api/orders` 需要登录返回的 token，模拟真实用户"登录一次，后续请求带头"。
- 配置步骤：
  - SetUp 线程组(1 个线程跑 1 次)：登录请求 + 后置处理器 JSON 提取器
    - JSON Extractor：变量名 `token`、JSONPath 表达式 `$.data.token`
    - JSR223 取样器把 token 写成全局属性：`${__setProperty(token,${token},)}`，供跨线程组使用
  - 主线程组(压测线程)：GET `/api/orders`
  - HTTP Header Manager：`Authorization: Bearer ${__P(token)}`
  - 响应断言：响应文本包含订单字段(如 `"orderId"`)
- **关键**：同一线程组内直接用 `${token}` 即可；跨线程组(SetUp → 主线程组)必须 `__setProperty` + `__P` 传参，这是关联的标准套路。
- **对应代码**：登录接口 `resp.json()["data"]["token"]` 存变量 → 业务请求 `headers={"Authorization": f"Bearer {token}"}`。

### 案例三：商品搜索接口压测(GET + 聚合报告看指标)

- 场景：搜索接口 `/api/search`，50 并发，验证吞吐量与响应时间。
- 配置步骤：
  - 线程组：线程数 50、Ramp-Up 5、调度器持续时间 60 秒(循环勾选"永远")
  - HTTP 请求：方法 GET、路径 `/api/search`、参数区填 `keyword=${keyword}`(CSV 参数化热门词)
  - 响应断言：状态码 200 + 响应包含"商品"
  - 聚合报告重点关注：Average、90% Line、Throughput、Error %
- **测开**：搜索类接口要覆盖空关键字、超长关键字、特殊字符等边界，呼应测试理论中的边界值分析。

### 案例四：文件上传接口压测

- 场景：图片上传接口 `/api/upload`，模拟用户传头像。
- 配置步骤：
  - HTTP 请求：方法 POST、路径 `/api/upload`、勾选 Use multipart/form-data for POST
  - 文件上传(Files Upload)区：文件路径 `C:\test\1.jpg`、参数名 `file`、MIME 类型 `image/jpeg`
- **注意**：上传压测易受压测机磁盘 IO 与带宽限制，TPS 上不去先看是不是压测机先到瓶颈，而非被测系统。

### 案例五：一次压测的完整流程

- ① 明确场景：哪个接口、目标并发、压多久、看哪些指标。
- ② 搭脚本：线程组 → HTTP 请求 → 断言 → 监听器，公共配置用 Request Defaults。
- ③ 本地调试：查看结果树，1 线程 1 次循环，确认请求参数、响应、断言全对。
- ④ 小规模验证：10 并发跑 1 分钟，看有无报错、数据是否失真。
- ⑤ 正式压测：命令行 `jmeter -n -t 脚本.jmx -l 结果.jtl -e -o 报告目录`。
- ⑥ 分析报告：聚合报告指标 + HTML 报告，结合业务判断是否达标。

### 实战排查(现象 → 定位 → 解决)

- **415**：Body Data 写了 JSON 但服务端不认 → 查 Header Manager 是否缺 `Content-Type: application/json`。
- **302**：接口跳转了但断言对不上 → 勾选 Follow Redirects，或看响应是不是落在中间跳转页。
- **乱码**：响应中文变问号 → 内容编码填 `UTF-8`。
- **全部超时**：线程全部挂起、TPS 为 0 → 检查服务器地址/端口是否可通，先 curl 验证接口本身通不通。
- **断言大面积失败但接口正常**：断言写错位置/条件 → 用查看结果树对比实际响应，检查断言与作用域。
- **TPS 上不去但压测机 CPU 100%**：压测机先到瓶颈 → 开分布式压测(JMeter Server 多台负载机)。

## 面试高频题

- **Q**：GET 和 POST 在 JMeter 中怎么配置？**A**：GET 参数放 Parameters(拼到 URL)；POST 表单也放 Parameters 或勾选 multipart；POST JSON 用 Body Data + Header Manager 设置 `Content-Type: application/json`。
- **Q**：POST 提交 JSON 报 415 怎么排查？**A**：先看 Header Manager 是否设置 `Content-Type: application/json`，再看 Body Data 是否是合法 JSON，最后确认编码是否 UTF-8。
- **Q**：压测登录后的接口，登录态怎么保持？**A**：加 HTTP Cookie Manager 自动保存并携带 Cookie；或用后置处理器提取 token，经 Header Manager 传 `Authorization`。
- **Q**：接口返回 302 怎么处理？**A**：勾选 Follow Redirects 跟随跳转记录完整链路；只需最终结果则用 Redirect Automatically。
- **Q**：响应中文乱码怎么办？**A**：请求内容编码填 `UTF-8`，或修改 `jmeter.properties` 默认编码。
- **Q**：多个接口重复填服务器地址太繁琐？**A**：用 HTTP Request Defaults 抽公共配置放线程组层，改环境只改一处。
- **Q**：压测要不要设响应超时？**A**：要。不设时服务端无响应线程会无限挂起，并发越积越多，压测结果失真。
