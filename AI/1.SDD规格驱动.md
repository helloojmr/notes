## SDD 是什么

- **SDD**（Spec-Driven Development，规范驱动开发）：**先写规范，再让 AI 按规范生成代码**——把 AI 从"代码生成工具"升级为"软件开发伙伴"。
- **与传统开发的差别**：传统是"需求 → 设计 → 编码 → 测试"；AI 时代 SDD 是"规范先行，代码后行"，规范是 AI 的唯一权威输入。
- **核心链条**：需求定义 → 规格说明 → 技术方案 → 任务分解 → 代码实现（What → Spec → Plan → Tasks → Code）。
- **三条原则**：意图驱动（规格写"做什么"，不写"怎么做"）、多步精炼（分步生成而非一次性）、规范约束（所有 AI 产出遵守项目宪法）。

## 主流实现：Spec Kit 与 OpenSpec

- **Spec Kit**：GitHub 官方开源的 SDD 工具包（github.com/github/spec-kit），提供 CLI + 斜杠命令，是当前主流标准。
- **OpenSpec**：以 `openspec/` 目录 + `changes/`（变更设计文档）为核心的另一套主流框架，强调**变更级**的规格管理。
- **共同点**：都用 Markdown 文件结构化需求、都面向 AI 代码生成、都支持可追溯开发。

### Spec Kit 的两个命令层

- **终端命令**：`specify init`（初始化项目结构）、`specify check`（环境检查）。
- **斜杠命令**（在 AI 助手聊天里用）：`/speckit.constitution`、`/speckit.specify`、`/speckit.plan`、`/speckit.tasks`、`/speckit.implement`。

## 核心工作流（五步）

1. **宪法**（constitution）：定项目最高规则——技术栈、编码规范、性能、安全，所有 AI 产出必须遵守。
2. **规格**（spec.md）：把模糊需求转成用户故事 + 功能需求（FR）+ 成功标准（SC），只写"做什么"。
3. **方案**（plan.md）：基于规格生成技术方案——架构决策（AD）、数据模型、接口契约。
4. **任务**（tasks.md）：把方案拆成可执行任务清单，支持分阶段跟踪。
5. **实现**（implement）：AI 按任务清单写代码，每个任务完成勾选。

## 文件清单与作用

- **constitution.md**（宪法）：定义项目核心原则（技术栈、安全要求、编码规范等全局约束），确保 AI 生成代码遵循统一标准。
- **spec.md**（规范）：描述功能需求、输入输出约束及验收标准，是 AI 实现的主要输入，明确"做什么"和"不做什么"。
- **design.md**（设计）：记录技术架构、接口定义、数据模型及模块拆分，把规范转化为可执行方案。
- **plan.md**（计划）：在规范后生成，定义实现步骤和时间安排，与 spec.md 配合（spec 定内容，plan 定方法）。
- **tasks.md**（任务）：把高级设计拆解为具体工作项，支持分阶段跟踪和验收，常按功能模块组织。
- **research.md**（研究）：记录背景调研、技术验证或可行性分析，辅助规范制定。
- **api.md**（API 文档）：专门描述接口契约（RESTful 端点、参数、响应格式），确保前后端协作一致性。
- **component.md**（组件文档）：聚焦 UI 或业务组件的详细设计，包括状态管理、事件处理等。
- **project.md**（项目信息）：概述项目背景、目标及范围，作为全局上下文参考。
- **AGENTS.md**（工作流说明）：定义 AI 智能体行为准则、团队协作规范及构建命令，支持多智能体协同。
- **changes/ 下的设计文件**（OpenSpec）：存储于 `openspec/changes/[变更名]/design.md`，记录单次功能变更的技术方案。

### 规格文件怎么用（关键点）

- **规格即验收标准**：spec.md 里的成功标准（SC）就是验收清单，实现完成后照着逐条过。
- **质量左移**：checklists/（质量检查清单）随规格生成，实现前就有验收口径。
- **可追溯**：需求（用户故事）→ 规格 → 任务 → 代码，一条链，定位问题快。
- **AI 产出验收**：AI 生成的功能对不对？对照 spec.md 的 FR/SC 验证——没有规格就无法验收 AI 产出。
- **测试人员价值**：能把需求写成无歧义规格（含边界、异常、性能约束）的人，决定 AI 产出质量。

## 标准目录结构

### Spec Kit 初始化结构

```
项目/
├── .specify/                  # 核心配置目录
│   ├── memory/
│   │   └── constitution.md    # 项目宪法（核心原则、治理规则）
│   ├── scripts/               # 自动化脚本（bash / powershell）
│   ├── templates/             # 文档模板（spec / plan / tasks）
│   └── workflows/             # 自动化 SDD 工作流定义
├── specs/                     # 功能级规格目录
│   └── 001-feature-name/      # 每个功能一个目录（编号-短名）
│       ├── spec.md            # 功能规格：用户故事 + FR + 成功标准
│       ├── plan.md            # 技术方案：架构决策 / 数据模型 / 契约
│       ├── tasks.md           # 任务清单
│       ├── research.md        # 研究记录（可选）
│       ├── contracts/         # API 契约文件（可选）
│       └── checklists/        # 质量检查清单
├── CLAUDE.md / GEMINI.md      # AI 助手上下文文件（脚本自动更新）
└── .claude/commands/          # 斜杠命令定义
```

### OpenSpec 结构

- `openspec/` 存项目级规范（project.md、AGENTS.md 等）
- `openspec/changes/[变更名]/` 存单次变更的 proposal.md + design.md + tasks.md

## 一个功能的完整生命周期（示例：任务管理应用）

### 宪法文件示例

```
# 项目宪法
## 技术原则
- 优先使用原生 Web API，避免不必要的第三方库
- 不使用任何框架（React、Vue 等）
## 代码质量
- 遵循 TDD，测试覆盖率 >= 85%
- 提交信息遵循 Conventional Commits
## 性能要求
- UI 交互响应时间 < 100ms
```

### 规格文件示例

```
# 任务管理功能规格
## 用户故事
- US-001：作为用户，我希望创建带名称、优先级、截止日期的任务
## 功能需求
- FR-001：系统必须支持任务创建，名称必填、优先级(高/中/低)、截止日期可选
- FR-002：任务列表支持按优先级筛选、按截止日期排序
## 成功标准
- SC-001：创建任务响应时间 < 100ms
- SC-002：筛选操作即时生效
```

### 方案与任务

- plan.md：架构决策（用 IndexedDB 存储、Web Components 组件化）+ data-model.md + contracts/
- tasks.md：拆成"创建任务表单 → 列表渲染 → 筛选排序 → 完成标记"逐项勾选
- **任务**（tasks.md）：拆成"创建任务表单 → 列表渲染 → 筛选排序 → 完成标记"逐项勾选。
- 实现：AI 按任务清单写代码，每完成一项勾选，全部勾完功能交付。

## 面试高频题

- **Q**：AI 时代 SDD 的核心流程？**A**：宪法 → 规格（spec）→ 方案（plan）→ 任务（tasks）→ 实现（implement），规范先行、代码后行。
- **Q**：Spec Kit 的目录结构？**A**：.specify/（宪法/脚本/模板/工作流）+ specs/（每个功能一个目录，含 spec/plan/tasks）。
- **Q**：spec.md 里一般写什么？**A**：用户故事、功能需求（FR）、成功标准（SC）——只写做什么，不写怎么做。
- **Q**：constitution.md 的作用？**A**：定义技术栈、编码规范、性能、安全等全局约束，所有 AI 产出必须遵守，防止自由发挥。
- **Q**：规格和需求文档的区别？**A**：规格面向 AI 生成、可执行、可追溯、有验收标准；需求文档只是意图描述。
