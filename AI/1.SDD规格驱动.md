## SDD 是什么

- **SDD**（Specification-Driven Development，规格驱动开发）：**规格（Specification）是开发的唯一权威输入**，代码、测试、文档都从规格派生。
- **规格不是需求文档**：需求文档描述"想要什么"，规格描述"系统在每种输入下必须产生什么输出"——是可判定对错的契约。
- **本质**：把"需求 → 代码"的跳跃，拆成"需求 → 规格（可验证）→ 代码（可对照）"两步。

## 规格的分层

- **业务规格**：用户故事 + 验收标准（AC），回答"业务上要达成什么"。
- **场景规格**：Given-When-Then 场景集，回答"每种情况下系统怎么表现"。
- **接口规格**：字段级契约（入参/出参/类型/约束/错误码），回答"系统边界上收什么发什么"。
- **数据规格**：字段字典、枚举值、关联规则，回答"数据长什么样"。
- **分层目的**：上层面向人（业务评审），下层面向机器（直接生成测试和代码）。

## 规格库落地结构（工程长什么样）

- SDD 在工程里 = **一个 specs/ 目录**，规格文件随代码进版本库、随需求变更走 review。
### 推荐结构

```
specs/
├── 00-index.md              规格索引：版本号、规格清单、变更记录
├── 01-business/             业务规格：用户故事 + 验收标准
│   └── auth.md              认证模块故事（登录/注册/找回密码）
├── 02-scenarios/            场景规格：Given-When-Then
│   └── auth-scenarios.md    登录的全部场景（成功/密码错/账号不存在…）
├── 03-api/                  接口规格：字段级契约
│   └── auth-api.md          POST /api/login 等接口契约
├── 04-data/                 数据规格：字段字典、枚举
│   └── user.md              用户表字段/状态枚举/约束
└── 05-generated/            派生产物（可自动生成，不入评审）
    ├── cases/               从规格展开的测试用例
    ├── mocks/               接口 mock 数据
    └── contracts/           契约测试文件
```

### 每个文件的职责

- **00-index.md**：看它就知道"这个系统有哪些规格、现在到哪个版本"——规格的入口。
- **01-business/*.md**：给产品/业务看，确认"我们要做的是不是这个"。
- **02-scenarios/*.md**：给开发和测试看，是**用例的母版**——每个场景 = 一条用例。
- **03-api/*.md**：给前后端和测试看，是**接口契约**——mock、联调、契约测试都靠它。
- **04-data/*.md**：数据字典，防"同一个字段两处叫法不同"。
- **05-generated/**：工具生成的中间产物，可随时重建，不进评审。

### 贯穿案例：登录（一个规格的完整链路）

#### 01-business/auth.md

```
用户故事：作为注册用户，我想要登录，以便进入个人中心。
AC1：账号密码正确时登录成功，返回 token。
AC2：密码错误时提示"密码错误"，不返回 token。
AC3：账号不存在时提示"账号不存在"。
```

#### 02-scenarios/auth-scenarios.md

```
场景：登录成功
  Given 账号存在且密码正确
  When 提交登录请求
  Then 返回 200，业务码 0，携带 token

场景：密码错误
  Given 账号存在、密码错误
  When 提交登录请求
  Then 返回业务码 1001，提示"密码错误"

场景：账号不存在
  Given 账号不存在
  When 提交登录请求
  Then 返回业务码 1002，提示"账号不存在"
```

#### 03-api/auth-api.md

```
接口：POST /api/login
入参：username(string,必填,3~32位)  password(string,必填,6~20位)
出参：code(int) data.token(string,成功时)
错误码：1001 密码错误 / 1002 账号不存在 / 1003 参数不合法
```

#### 04-data/user.md

- 用户表字段：id / username / status…
- status 枚举：0 正常 / 1 禁用
- **05-generated/cases/**：由 02/03 展开出的用例文件（登录参数化用例：边界 2/3/32/33 位等）。
- **验证**：实现完成后，测试照着 02 的场景 + 03 的契约逐条跑，全绿 = 规格达成。

## 与 TDD / BDD / DDD 的关系

- **TDD**：测试先行，关注"怎么写才正确"（微观，方法级）。
- **BDD**：行为驱动，用 Given-When-Then 让业务参与，关注"怎么描述需求"（表达层）。
- **DDD**：领域驱动，关注"领域模型怎么设计"（架构层）。
- **SDD**：规格先行，关注"先定行为契约再实现"（流程层）。
- **关系**：SDD 是流程框架，内嵌 BDD 表达规格，用 TDD 做实现验证，用 DDD 定边界——不冲突，互补。

## 工作流程

1. **写规格**：按 specs/ 结构产出四层规格，格式可读且可机器解析。
2. **评审规格**：业务、开发、测试三方评审；用场景穷举法找歧义（"如果…怎么办"逐个问）。
3. **规格入库**：规格随代码一起 review、一起发版（改代码必先改规格）。
4. **派生产物**：从规格生成测试用例、mock、契约测试（05-generated/）。
5. **验证闭环**：规格驱动的测试逐条对照，任何一条不通过 = 规格或实现有问题。
6. **变更管理**：需求变化先改规格 → 评估影响范围 → 改代码 + 回归对应用例。

## AI 时代的 SDD（关键）

- **规格 = 给 AI 的提示词**：AI 生成代码/用例/文档的质量，上限取决于规格质量。
- **人机协作**：人写规格（业务理解不可替代）→ AI 按规格生成实现 + 测试 + 文档。
- **AI 产出验收**：没有规格，AI 产出无法验证；有规格，验证 = 逐条对照。
- **测开新价值**：会写高质量规格（含边界/异常/性能约束）的人决定 AI 产出质量——规格工程师。

## 测开落地要点

- **Spec-to-Case 管线**：接口规格 → 自动展开等价类/边界/错误码用例，减少手写。
- **规格覆盖率**：度量"哪些规格点没有对应用例"（像代码覆盖率一样）。
- **契约测试**：接口规格即契约，消费方和提供方各跑契约测试，防两端漂移。
- **可测试性前置**：规格阶段就暴露"这需求没法测"，倒逼需求澄清。

## 面试高频题

- **Q**：SDD 和 TDD 的本质区别？**A**：TDD 用测试表达"怎么做"，SDD 用规格表达"做什么"；SDD 更早介入需求层，测试是规格的验证落地。
- **Q**：SDD 的规格库长什么样？**A**：specs/ 目录按业务/场景/接口/数据分层，加索引和派生产物，随代码版本管理。
- **Q**：AI 时代 SDD 为什么更重要？**A**：规格是 AI 生成的唯一权威输入，规格质量决定 AI 产出质量。
- **Q**：怎么让规格可验证？**A**：场景化（Given-When-Then）+ 字段级契约（类型/边界/错误码），每条可翻译成可判定用例。
