## SDD 是什么

- **SDD**（Specification-Driven Development，规格驱动开发）：**先写规格（Specification），再写代码**的开发方法。
- **规格** = 用结构化语言描述"系统该做什么"（需求的行为契约），而不是"怎么做"。
- **核心转变**：从"边想边写代码"→"先定清楚行为规则，代码照着规格实现"。
- **一句话**：代码是实现，规格是法律。

## 核心思想

- **规格先行**：动手写代码前，先把行为的输入/输出/边界/异常定清楚。
- **规格即文档**：规格本身是活的文档，替代传统"需求文档 + 设计文档"两层皮。
- **规格即测试依据**：每条规格都能翻译成测试用例，天然可验证。
- **人机共识**：规格是人和 AI（或人和人）之间无歧义的沟通载体。

### 与 TDD / 传统开发对比

- **传统**：需求文档 → 设计 → 编码 → 测试（测试最后才介入，需求漂移难追）。
- **TDD**（测试驱动）：先写失败的测试，再写代码让测试通过（测试先行）。
- **SDD**：先写规格（行为规则），再实现 + 验证（规格先行，测试是规格的落地形式）。
- **区别**：TDD 从"用例"出发，SDD 从"行为规格"出发；SDD 更强调**需求层的无歧义**。

## 工作流程

1. **写规格**：用自然语言 + 结构化格式描述行为（做什么、输入、输出、边界）。
2. **规格评审**：人审或 AI 辅助审，确认无歧义、无遗漏。
3. **实现**：按规格逐条实现功能。
4. **验证**：把规格翻译成测试用例，逐条验证实现是否符合规格。
5. **迭代**：需求变化 → 改规格 → 改代码 → 重新验证。

## 规格怎么写

- **用户故事**：作为 XX，我想要 XX，以便 XX。
- **Given-When-Then**（行为驱动，最常用）：
  - Given 前置条件 → When 触发动作 → Then 期望结果。
- **验收标准**（AC，Acceptance Criteria）：每条故事附 1~N 条可验证的 AC。
- **结构化字段**：输入、输出、错误场景、边界值、性能要求。

### 示例

```
用户故事：作为注册用户，我想要登录，以便进入个人中心。

场景 1：登录成功
  Given 账号密码正确
  When 提交登录请求
  Then 返回 200，携带 token，跳转个人中心

场景 2：密码错误
  Given 账号存在、密码错误
  When 提交登录请求
  Then 返回业务码 1001，提示"密码错误"
```

## 测开视角

- **规格 = 测试用例的母版**：每条 Given-When-Then 直接映射一条用例，测开从"猜需求"变成"翻译规格"。
- **可测试性设计前移**：规格阶段就明确输入/输出/边界，测试左移落到实处。
- **需求漂移可追溯**：规格变更 → 用例变更 → 回归范围明确，改一处不慌。
- **AI 协作**：让 AI 根据规格生成用例、生成测试数据、甚至生成实现；人负责评审规格。

## 面试高频题

- **Q**：SDD 是什么？和 TDD 有什么区别？**A**：SDD 先写行为规格再实现，强调需求无歧义；TDD 先写失败测试再实现，强调测试驱动；SDD 的验证层落地为测试，两者可结合。
- **Q**：SDD 对测试工程师有什么好处？**A**：规格即用例母版，测试左移，需求漂移可追溯，减少"猜需求"。
- **Q**：Given-When-Then 怎么用？**A**：前置条件→触发动作→期望结果，每条可独立验证。
