## SDD 是什么

- **SDD**（Specification-Driven Development，规格驱动开发）：先定"系统必须产生什么行为"（规格），代码和测试都从规格派生。
- **SDD 的工程形态**：规格不是散文档，而是**一套结构化、进版本库、可执行、可追溯的规格库**——规格即代码。

## 规格库：目录结构与文件清单

- 大型项目通常用**独立规格仓库**（specs repo），代码仓库通过子模块/引用关联；中小项目放在主仓库根目录。

### 完整目录结构

```
specs/                          # 规格库根目录（独立仓库或主仓库子目录）
├── README.md                   # 规格库说明：怎么读、怎么改、怎么评审、谁负责
├── VERSION.md                  # 规格总版本 + 兼容性说明（semver）
├── CHANGELOG.md                # 规格变更记录（每次评审通过追加一条）
├── CONTRIBUTING.md             # 提交流程：新增/修改规格的步骤与评审要求
│
├── 01-requirements/            # 第 1 层：业务规格（需求故事 + 验收标准）
│   ├── auth/
│   │   ├── AUTH-101-login.md       # 用户故事：作为XX，想要XX，以便XX + AC 列表
│   │   └── AUTH-102-register.md
│   └── order/
│       └── ORD-201-create.md
│
├── 02-scenarios/               # 第 2 层：场景规格（Gherkin .feature，可执行）
│   ├── auth/
│   │   ├── login.feature          # 登录全部场景：成功/密码错/锁定/参数非法…
│   │   └── register.feature
│   └── order/
│       └── create-order.feature
│
├── 03-api/                     # 第 3 层：接口规格（OpenAPI 契约）
│   ├── auth-api.yaml            # OpenAPI 3.x：路径/入参/出参/错误码/鉴权
│   ├── order-api.yaml
│   └── schemas/                 # 复用的数据结构定义
│       ├── user.yaml
│       └── common.yaml          # 通用响应包装（code/message/data）
│
├── 04-data/                    # 第 4 层：数据规格
│   ├── dictionary.md            # 字段字典：全库字段名/类型/含义
│   └── enums/                   # 枚举与状态机
│       ├── order-status.md      # 订单状态流转（待支付→已支付→已发货→…）
│       └── user-status.md
│
├── 05-contracts/               # 第 5 层：契约测试（消费方/提供方）
│   ├── consumers/               # 消费方契约（Pact 等生成）
│   └── providers/               # 提供方契约
│
├── 06-mocks/                   # 第 6 层：mock 数据与 mock 服务
│   ├── auth/
│   │   └── login-ok.json        # 各接口的成功/失败 mock 报文
│   └── openapi-mock.md          # 由 OpenAPI 自动生成 mock 的说明
│
├── 07-traceability/            # 第 7 层：追溯矩阵
│   └── traceability.md          # 故事→场景→接口→用例→代码 关联表
│
└── 08-governance/              # 第 8 层：治理文件
    ├── review-checklist.md      # 规格评审检查清单（边界/异常/口径/可测性）
    ├── decisions.md             # ADR：架构/契约关键决策记录
    └── metrics.md               # 规格覆盖率等度量口径
```

## 每个文件的职责（实际怎么用）

- **README.md**：新人入口——看它就知道规格库怎么组织、找规格从哪开始。
- **VERSION.md + CHANGELOG.md**：规格有版本、有变更历史；接口 v1.0 → v1.1 兼容说明写这里，消费方按版本对接。
- **01-requirements/**：业务侧确认"做的是不是这个"；故事 ID 全局唯一，后续层级都引用它。
- **02-scenarios/**：**测试的主战场**——每个 .feature 场景 = 一条自动化用例，Cucumber/Behave 直接执行。
- **03-api/**：前后端联调契约 + 契约测试依据；OpenAPI 自动生成文档、mock、客户端。
- **04-data/**：字段字典和枚举，防"同字段两处定义"；状态机单独管。
- **05-contracts/**：契约测试产物，CI 里自动验证两端不漂移。
- **06-mocks/**：联调和测试用的 mock 报文，接口没好的时候测试不阻塞。
- **07-traceability/**：改一条规格，查影响范围（哪些用例/代码要回归）。
- **08-governance/**：评审标准、关键决策、度量——规格库的"制度"。

## 关键设计（和玩具规格的区别）

- **规格即代码**：所有文件进 Git、走 MR review、有 CI——不是"写完就完"的文档。
- **CI 自动校验**：
  - OpenAPI 文件过 `spectral` 规范校验 + 格式校验。
  - .feature 过 Gherkin 语法校验，提交即跑场景。
  - 契约测试随 CI 跑，任何一端漂移立刻红。
- **版本管理**：规格整体有 semver 版本；接口变更按"兼容/不兼容"分级走流程。
- **变更必走评审**：改规格 = 改代码，MR 里附变更说明 + 影响分析，评审通过才合入。
- **规模适配**：
  - 小项目/单人：保留 01~04 四层 + README 即可，05~08 按需。
  - 大型项目/多团队：独立 specs 仓库 + 分层负责人（接口组管 03，测试组管 02）+ CI 门禁。

## 面试高频题

- **Q**：SDD 的规格库一般有哪些目录？**A**：requirements（业务）、scenarios（场景）、api（接口契约）、data（数据字典）、contracts（契约测试）、mocks、traceability（追溯）、governance（治理），加 README/版本/变更记录。
- **Q**：规格库怎么保证不流于形式？**A**：规格即代码进 Git、CI 校验（OpenAPI 规范/feature 语法/契约测试）、变更走评审、追溯矩阵关联用例。
- **Q**：规格版本怎么管？**A**：整体 semver + CHANGELOG，接口按兼容/不兼容分级，消费方按版本对接。
- **Q**：大型和小项目规格库差在哪？**A**：小项目保留核心四层；大型项目独立 specs 仓库、分层负责人、CI 门禁、完整治理文件。
