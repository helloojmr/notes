
## 1. 为什么需要判定表
- 等价类和边界值主要关注单个输入，但当多个条件组合决定输出时（如业务规则），需要一种方法覆盖所有逻辑组合。判定表就是为此而生。
- 判定表适用于**条件与动作之间存在复杂逻辑**的场景，如优惠券计算、权限控制、状态机。在自动化测试中，我们可以用**规则引擎**或**参数化组合**来覆盖判定表。
## 2. 判定表结构
- **条件桩**：列出所有可能影响结果的条件。
- **动作桩**：列出所有可能采取的操作。
- **条件项**：每个条件可能的取值（通常为布尔值，也可多值）。
- **动作项**：对应条件组合下应该执行的动作。
	
## 3. 设计步骤

1. 明确需求，列出所有条件和动作。
2. 确定条件个数 n，规则数最多为 2^n（每个条件取真/假）。
3. 填写条件项和动作项，形成完整判定表。
4. 合并相同动作的规则（可选），简化用例。

- **列出条件和动作**
  - 手工做法：从需求提取
  - **测开**：分析代码中的if-else逻辑，提取所有条件分支
- **填写条件项**
  - 手工做法：手动枚举组合
  - **测开**：用Python的`itertools.product`生成所有条件组合，再过滤无效组合
- **编写用例**
  - 手工做法：每条规则一条用例
  - **测开**：用数据驱动，自动生成测试数据，调用被测接口验证预期动作

## 4. 案例：欠费/关机与主被叫权限

- 是否欠费：是否关机；是：是；是：否；否：是；否：否
- **动作**
  - 是否欠费：允许主被叫
  - 是：否
  - 是：否
  - 否：否
  - 否：是


- 规则1：欠费且关机 → 不允许
- 规则2：欠费不关机 → 不允许
- 规则3：不欠费关机 → 不允许（因为关机无法通信）
- 规则4：不欠费不关机 → 允许
## 5. 适用场景
- 多条件逻辑组合
	- 优惠券计算：满减、折扣、门槛、用户等级、商品类型等条件组合。
	- 权限控制：不同事件下状态变化（如支付成功、发货、取消）。
	- 状态流转：角色、资源、操作类型的组合。
- 例题
	- Q：如何处理条件组合爆炸（条件过多）？
	- A：通常不会全组合，而是：
		- 正交试验法（Pairwise）减少用例
		- 分析业务优先级，只覆盖高风险的组合
		- 用代码逻辑分析，合并等价条件（如某些条件互斥）
		- 对核心逻辑用判定表全覆盖，边缘用错误推测补充
