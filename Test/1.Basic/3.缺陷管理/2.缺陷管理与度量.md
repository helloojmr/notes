## 缺陷的字段属性
- **1. 严重程度（Severity）**
指缺陷对系统的影响程度。常见划分：
	- **致命（Blocker）**：导致系统崩溃、数据丢失、主要功能不可用。
	- **严重（Critical）**：主要功能受影响，但系统可运行（如支付失败）。
	- **一般（Major）**：次要功能受影响，或有明显错误。
	- **轻微（Minor）**：界面错位、提示语不友好等。
	- **建议（Enhancement）**：改进性建议。
- **2. 优先级（Priority）**
指缺陷需要被修复的紧急程度。通常由测试和项目组根据业务确定：
	- **P0（最高）**：必须立即修复，否则无法发版（如阻塞性bug）。
	- **P1（高）**：应尽快修复，影响核心功能。
	- **P2（中）**：可以稍后修复，但应在发版前解决。
	- **P3（低）**：可选修复，可延期或后续版本。
- **3. 缺陷类型（Type）**：
便于后续统计分析，常见：
	- 功能错误、UI界面、兼容性、性能、安全性、易用性、文档错误、建议等。
	- 可增加“自动化遗漏”类型，用于统计哪些缺陷本可以被自动化发现但没覆盖，从而指导自动化测试的改进。
- **重要关系**：
	- 严重程度和优先级不一定成正比。例如，一个界面错位（轻微）但发生在核心入口（如“登录”按钮），可能会被定为高优先级。
	- 测试人员通常只定义严重程度，优先级由项目组综合决定。
## 缺陷管理流程与注意事项
### 流程
1. 提交缺陷
2. 分配缺陷
根据模块自动分配给对应开发（通过代码库的OWNERS文件）。
3. 重复？bug
用NLP算法自动识别相似缺陷，提醒可能重复。
4. 推迟？处理/后续版本
5. 验证，回归
缺陷修复后，自动触发对应的自动化用例，验证通过则自动关闭。
6. 关闭
### 提交注意事项
1. 可重现（缺陷可以复现）
自动化用例本身就是可重现的。缺陷提交时，可附带一条**最小可重现的自动化脚本**。
2. 唯一性（一个缺陷上报一个问题）
一个缺陷一个用例。自动化测试也遵循此原则，每条用例独立。
3. 规范性（符合公司或者项目要求）
统一缺陷模板，用工具自动生成。
4. 缺陷编写规范
	1. 准确（描述的信息是正确的）
	2. 具体（有细节且是真实特定的）
	3. 简洁易懂（描述简单容易理解）
	4. 次序清晰（描述缺陷过程有条件，有先后顺序）
	5. 缺陷优先级划分
		1. 1级---冒烟正向业务用例
		2. 2级---冒烟逆向业务用例及单功能正向
		3. 3级---单功能逆向及UI布局
		4. 4级---建议
- Q：你如何确保提交的缺陷是可重现的？A：我提交缺陷时，会附带：
	- 具体的环境信息（Docker镜像版本、数据库数据）
	- 一条可执行的自动化脚本（如pytest函数），包含完整的步骤和断言
	- 如果有条件，录制一段自动化执行视频  
	- 这样开发可以直接运行脚本复现，极大提高沟通效率。


## 缺陷分析与质量度量

-  **缺陷密度**
每千行代码的缺陷数，衡量代码质量。
   - **自动化统计**：通过代码扫描工具（如SonarQube）结合测试管理工具，自动计算每千行代码缺陷数。
   - **可视化**：用图表展示各模块缺陷密度，识别高风险模块。
-  **缺陷引入阶段**
需求、设计、编码、测试阶段分别引入多少bug，用于改进流程。
   - **数据来源**：在缺陷系统中增加字段"引入阶段"，测试人员填写。
   - **自动化分析**：通过版本对比（Git diff），结合缺陷修复文件，自动推测引入阶段。
-  **缺陷修复时长**
平均修复时间，衡量团队响应速度。
   - **自动化监控**：从缺陷系统API获取创建时间和解决时间，生成报表，异常时长自动告警。
-  **缺陷闭合率**
一定时间内关闭的缺陷比例。
   - **看板**：用Grafana等工具实时展示缺陷趋势。
-  **逃逸缺陷（线上bug）**
上线后发现的缺陷，反映测试覆盖的不足。
   - **自动化回归**：每个线上缺陷都转化为自动化用例，防止再次逃逸。
   - **根因分析**：组织复盘，将常见原因（如测试环境与生产环境不一致）转化为改进项。

- **实战要点**：
  - 开发**缺陷度量看板**，从Jira等系统实时拉取数据，展示在团队大屏上。
  - 通过分析历史缺陷，总结高频出错模块，指导自动化测试的投入重点。
  - 利用机器学习预测缺陷风险模块，提前加强测试。

- **Q**：你做过哪些缺陷分析？如何驱动质量改进？
**A**：我每周会从Jira导出缺陷数据，从多个维度分析：
    - **按模块**：找出缺陷最多的模块，推动开发重构或增加单元测试。
    - **按类型**：如果"边界条件"类缺陷多，组织专项测试；如果"环境"类缺陷多，优化测试环境（如容器化）。
    - **按引入阶段**：若需求阶段缺陷多，加强需求评审和测试左移。
    - **逃逸缺陷**：每个线上bug都转化为自动化用例，并分析为何漏测，改进测试设计。
    - 同时，我会开发一个质量看板，实时展示缺陷趋势，让团队一眼看清质量状况。
