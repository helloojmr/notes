## 断言基础

### 断言是什么

- **定义**：验证请求的响应是否符合预期，断言失败则该采样被标记为错误(红色)。
- **对应代码**：Python 的 `assert`，接口自动化里的"校验点"。
- **位置**：右键 HTTP 请求 → 添加 → 断言 → 选择断言类型。
- **实战要点**：断言 = 测试用例的"预期结果"，没有断言的请求只是"发了"，不叫"测了"。

### JMeter 自动判断响应状态码

- **默认机制**：不用写任何断言，JMeter 自动把 4xx/5xx 响应标记为失败(查看结果树红色)，2xx/3xx 标记为成功(绿色)。
- **为什么还要写断言**：**状态码 200 不代表业务成功**——登录失败常见返回 200 + `"code":1`，自动判断不报错，必须用响应断言校验业务码。
- **两层防线**
  - 状态码层：JMeter 自动判，覆盖网络层/HTTP 层错误(404、500、超时等)
  - 业务层：响应断言手动判，覆盖业务逻辑错误(200 但 code 非 0)
- **负向用例注意**：期望返回 4xx 的用例(如校验非法参数返回 400)会被自动标红，常规压测主流程用 2xx + 业务码校验，负向用例另行处理。
- **面试话术**：JMeter 自动判状态码只覆盖 HTTP 层错误；业务失败必须靠断言——"接口返回 200 但业务失败"是接口测试最经典的坑。

## 断言类型

### 响应断言(最常用)

- **位置**：HTTP 请求 → 添加 → 断言 → 响应断言。

#### 测试字段(Apply to)

- 选择校验响应的哪一部分。
- **响应文本**：响应 body 内容，最常用
- **响应代码**：状态码，如 200 / 400 / 500
- **响应消息**：状态描述，如 OK / Not Found
- **响应头**：如 Content-Type
- **URL 样本**：请求的 URL
- **忽略状态**：自动忽略网络状态码判断机制

#### 模式匹配规则

- **包含(Contains)**：响应中包含指定内容(子串)，最常用
- **匹配(Matches)**：用正则完整匹配整个响应
- **相等(Equals)**：响应与内容完全相等
- **字符串(String)**：包含指定字符串(可忽略大小写)

#### 多模式与示例

- **多模式**：可添加多行，多行之间是 **AND 关系**(全部满足才通过)。
- **示例**：登录接口断言"响应文本"包含 `"code":0` 或 `登录成功`。

### JSON 断言

- **作用**：直接校验 JSON 字段值，比响应文本精确。
- **配置**：JSON Path 表达式(如 `$.code`) + 期望值(如 `0`) + 是否允许空值。
- **适用**：接口返回 JSON 时，校验业务码、token 等关键字段。
- **对应代码**：`assert resp.json()["code"] == 0`。

### 断言持续时间(Duration Assertion)

- **作用**：响应时间超过阈值判定失败，性能测试专用。
- **配置**：填毫秒值，如 500 表示响应超过 500ms 即失败。
- **场景**：压测时验证接口是否满足响应时间要求(如 P95 < 500ms)。

### 其他断言(了解)

#### 大小断言(Size Assertion)

- 校验响应字节数是否在范围内。

#### HTML 断言

- 校验 HTML 标签/页面内容，Web 页面场景用。

## 断言使用

### 使用要点

- **作用域**：放线程组层 → 组内所有请求都断言；放单个 HTTP 请求下 → 只对该请求生效。
- **多条件**：同一断言元件内多行 = AND；需要 OR 时用多个断言元件。
- **失败表现**：查看结果树里该请求变红叉，聚合报告 Error% 上升。
- **调试技巧**：先用查看结果树看实际响应长什么样，再写断言，避免凭猜写。
- **面试话术**：断言写好后先单线程跑一遍验证通过，再上并发，否则压测结果里错误率全是断言误报。

### 校验三层

- **状态码层**：HTTP 200，网络层通不通——**JMeter 自动判断，无需写断言**。
- **业务码层**：响应体里的 code，如 0 成功 / 1 失败，业务逻辑对不对。
- **关键字段层**：token 非空、数据条数、金额正确，数据对不对。
- **对应代码**：`assert resp.status_code == 200` → `assert resp.json()["code"] == 0` → `assert resp.json()["data"]["token"]`。
- **实战要点**：三层都断言的用例才是合格用例；只断状态码的断言≈没断言。

## 实战案例

### 案例一：登录接口断言组合

- 场景：压测登录，要确保"请求真的成功"。
- 配置：
  - 响应断言：测试字段"响应代码"，匹配规则"相等"，内容 `200`
  - 响应断言：测试字段"响应文本"，匹配规则"包含"，内容 `"code":0`
  - JSON 断言：`$.data.token` 期望"非空"
- 效果：状态码、业务码、关键字段三层全校验。

### 案例二：搜索接口性能断言

- 场景：搜索接口压测，要求响应时间达标。
- 配置：
  - 响应断言：响应文本包含 `商品`
  - 断言持续时间：500(ms)
- 效果：错误率里会区分"业务失败"和"响应超时"，定位问题快。

## 面试高频题

- **Q**：响应断言的测试字段有哪些？**A**：响应文本、响应代码、响应消息、响应头、URL 样本；最常用响应文本。
- **Q**：包含、匹配、相等有什么区别？**A**：包含是子串包含；匹配是正则完整匹配整个响应；相等是完全相等；一般业务校验用"包含"即可。
- **Q**：同一断言里多行模式是什么关系？**A**：AND，全部满足才通过；需要 OR 用多个断言元件。
- **Q**：性能测试用哪个断言？**A**：断言持续时间(Duration Assertion)，校验响应时间阈值，超时即失败。
- **Q**：断言大面积失败但接口正常怎么排查？**A**：先看查看结果树里实际响应与断言内容是否一致，多半是断言内容写错或作用域放错层级。
