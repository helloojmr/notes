## 性能测试指标

> 性能测试需要通过量化指标来客观衡量系统性能的好坏。

### 1. 响应时间（Response Time）

- 指的是从客户端发送一个请求开始，到客户端收到响应结果为止，中间所耗费的总时间。
  - 响应时间可用于接口测试，如通过 Postman 或 Python 代码发送请求并统计响应时间。
  - 接口测试中通常使用 HTTP 请求进行性能测试。
  - 包括两个主要部分：
    - 网络传输时间
    - 服务器处理时间
  - **补充：响应时间分位数（PXX）**——压测评估的重点
    - 平均响应时间容易被极端值（长尾请求）拉高，不能只看平均值。
    - 常用分位数：
      - **P50（中位数）**：50% 的请求在该值以内完成。
      - **P90**：90% 的请求在该值以内完成。
      - **P95**：95% 的请求在该值以内完成。
      - **P99**：99% 的请求在该值以内完成（代表最差体验）。
    - **面试话术**：压测报告同时给出平均值和 P95/P99。若 P99 明显高于 P50，说明存在长尾请求，可能是慢 SQL、锁等待、GC 停顿等导致。

### 2. 并发数（Concurrency）

- 同一时刻同时向服务器发送请求的用户数，用于衡量系统在单位时间内所承受的真实负载。
- **在线用户数 ≠ 并发数**：在线用户只是"挂着"，不产生请求；并发数是真正同时发起请求的用户。例如在线 10 万用户，并发可能只有几百。

### 3. 吞吐量（Throughput）

- 单位时间内处理客户端请求数量的能力，直接衡量软件系统的性能承载能力。
- 吞吐量的衡量角度：
  - **业务角度**：以完成的业务数量为单位，如一天成交多少笔交易，主要面向用户展示。
  - **网络角度**：以单位时间传输的字节数为单位，如每小时字节数，用于衡量系统流量。
  - **技术角度**：重点关注每秒事务数（TPS）和每秒查询数（QPS），是性能测试中的核心指标。
    - **QPS**（Queries Per Second）：指系统每秒能处理的 HTTP 请求的数量。QPS 不是系统整体的固定值，而是针对特定请求类型的处理能力上限，每个请求都有其最大 QPS。
    - **TPS**（Transactions Per Second）：指系统每秒能够处理的事务数量，一个事务可能对应一个或多个底层请求。

### 4. 点击数（Hits）

- 点击数指客户端向服务器发送请求时，**所有页面资源元素的请求总数量**。
- 以访问百度网页为例，点击搜索按钮后，抓包显示共发出 49 个请求，其中仅第一个为搜索动作本身，其余为图片、GNS、CSS 等页面元素加载请求。这 49 个请求的总和即为"点击数"，它表示一次用户操作引发的所有资源加载请求数量，而非单纯的页面点击行为。
- **事务不包含页面元素加载所产生的大量请求**，而点击数则包含这些资源请求（如图片、CSS 文件等）。

### 5. 错误率（Error Rate）

- 错误率指在负载情况下，失败的业务数占总业务数的比例，是一个性能指标。
- **错误率必须基于负载测试场景**，即高并发、多用户、大量请求同时发生的情况。
- 点击数关注资源请求总量，错误率关注高负载下的业务失败概率，二者均为性能监控关键点，需与功能测试概念明确区分。

### 6. 资源利用率（Resource Utilization）

- 资源利用率即系统各项配置资源（CPU、内存、磁盘、网络）的使用情况。
- 一般关注：CPU 使用率、内存使用率/剩余、磁盘 IO（%util、await）、网络带宽（进/出流量）。

### 7. 性能曲线与拐点（Performance Curve）

- 以**并发数为横轴**、**TPS / 响应时间为纵轴**绘制曲线，是分析系统性能承载能力的核心方法。
- 典型三个阶段：
  - **线性增长区**：并发增加，TPS 线性上升，响应时间平稳——系统处于最佳工作区。
  - **拐点（饱和点）**：TPS 增速放缓直至不再上升，响应时间开始明显上升——此时对应的并发即为**最佳并发数**，TPS 为**最大 TPS**。
  - **过载区**：继续加压，TPS 不升反降，响应时间飙升，错误率上升。
- **测开**：压测时逐步加压（如 10 → 50 → 100 → 200 → 400），配合监控记录每个并发档位的 TPS 与响应时间，绘制曲线找到拐点，确定系统的最大承载能力与最佳并发区间。

## 性能测试流程

> 性能测试流程包括**需求分析、计划与方案、用例设计、执行、bug 分析调优、报告总结**六个阶段。

- **需求分析**
  - 做什么：明确性能需求：指标（TPS/RT/错误率/资源）、业务场景、并发预估
  - 产出：性能需求清单、验收标准
- **计划与方案**
  - 做什么：确定测试范围、工具选型（JMeter/Locust）、环境与数据准备、时间安排
  - 产出：性能测试方案
- **用例设计**
  - 做什么：设计场景模型（业务占比/用户模型）、性能测试用例（场景+指标+数据）
  - 产出：性能测试用例
- **执行**
  - 做什么：按方案执行压测：基准 → 负载 → 稳定性 → 压力；同步监控系统资源
  - 产出：压测数据、监控记录
- **Bug 分析调优**
  - 做什么：定位瓶颈（见第五章）、推动优化、回归验证
  - 产出：瓶颈分析报告、优化记录
- **报告总结**
  - 做什么：输出性能测试报告：指标数据、曲线、结论、遗留风险、上线建议
  - 产出：性能测试报告
